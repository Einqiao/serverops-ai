# 开发任务

## 需求

将 ServerOps AI 拆分为一个运行在 DMP 之外的 Python 服务，完成服务器状态与日志获取、异常检测、AI 辅助诊断、故障记录和可视化展示。

## AI辅助方式

开发过程中使用 Cursor 等 AI Coding 工具辅助完成需求拆解、代码阅读、模块设计、初步实现和问题定位。

使用方式是按照功能模块逐步推进：先让 AI 阅读和分析现有代码，再拆分开发任务，完成后通过实际运行、测试和人工检查验证结果；发现问题后继续定位和修复。


## 任务拆分

- 配置和 DMP 客户端：负责连接参数、登录和只读 API。
- Collector：分别采集服务器状态、在线玩家和日志。
- Detector：用可解释规则识别常见异常。
- Diagnosis：统一现场上下文并调用结构化 LLM Provider。
- Storage：使用 SQLite 保存 Incident 和 Webhook 事件。
- Dashboard：展示实时状态、趋势和故障详情。
- Webhook：提供可选的 DMP 事件接收入口。

## 实现过程

项目最终形成了 `app`、`collector`、`detector`、`llm` 和 `storage` 等目录。`app/main.py` 负责配置加载、依赖装配、一次性执行和轮询入口；具体能力由各模块提供，避免把 DMP 请求、规则、数据库和页面逻辑全部放在入口文件中。

实现过程中先完成 DMP 连接、服务器状态与日志采集，再逐步接入规则检测、结构化诊断、Incident 持久化和 Dashboard。开发过程中优先保证核心链路能够独立运行，再逐步增加外围能力，避免多个功能同时开发导致问题难以定位。

在完成基础链路后，对各模块进行了独立验证，并保持采集、检测、诊断、存储和展示之间的职责边界。

## 人工检查

人工检查了项目目录、配置示例、入口装配以及各模块之间的调用关系，重点确认：

- DMP 访问由 `DMPClient` 统一封装。
- Collector、Detector、Diagnosis、Storage 和 Dashboard 保持相对独立。
- 规则检测和 LLM 诊断是可替换的独立步骤。
- Dashboard 通过既有状态和 Incident 数据提供展示，不重复实现业务逻辑。
- 数据库负责 Incident 的保存和查询。

## 遇到的问题

项目同时涉及 DMP API、日志采集、规则检测、LLM 诊断和 Dashboard，如果直接在入口层串联所有逻辑，后续调试和替换都会比较困难。

另外，LLM 属于外部依赖，响应格式和网络状态存在不确定性，因此需要保证核心规则检测链路不依赖模型才能正常运行。

因此开发过程中重点将外部依赖和核心业务逻辑进行拆分，使 DMP、规则检测、LLM Provider 和 Dashboard 都可以独立验证。

## 修复与验证

通过拆分客户端、采集器、检测器、诊断、存储和页面模块，建立清晰的模块边界，并保证外部依赖异常时核心检测链路仍可独立运行。

验证过程中没有只依赖 AI 生成结果，而是结合实际运行结果进行人工检查。现有验证包括真实 DMP 只读联调、Python 模块编译、规则检测、Mock 诊断链路、Incident 保存和 Dashboard 访问，确认各模块可以按照预期串联运行。
